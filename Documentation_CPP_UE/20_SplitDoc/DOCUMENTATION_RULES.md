# DOCUMENTATION RULES

Правила создания и обновления Markdown-документов проекта C++ / Unreal Engine.

## 1. Когда читать

Документ обязателен, если задача:

- создаёт или меняет Markdown;
- меняет структуру Documentation_CPP_UE/;
- переносит правила;
- добавляет постоянное правило;
- обновляет task-loop, START, SplitDoc или Project_Docs;
- создаёт новый документ или предлагает его название.

Также читать Documentation_CPP_UE/20_SplitDoc/ENCODING_RULES.md.

## 2. Канонические пути

- Главная документация: Documentation_CPP_UE/.
- Текущая задача: Documentation_CPP_UE/11_Задача_агенту.md.
- START: Documentation_CPP_UE/12_Старт_агента.md.
- Тематические правила: Documentation_CPP_UE/20_SplitDoc/.
- История: Documentation_CPP_UE/20_SplitDoc/TASK_HISTORY.md.
- Очередь: Documentation_CPP_UE/05_Очередь_задач.md.
- Проектные документы: Documentation_CPP_UE/21_Project_Docs/.

Постоянные пути задаются относительно корня репозитория. Локальный абсолютный путь допустим только в разовой диагностике и не становится каноническим правилом.

## 3. Scope и источник правды

Документы создаются и меняются только по задаче пользователя или активному БЛОКУ 1.

Агент:

1. проверяет, существует ли уже документ с тем же назначением;
2. выбирает один канонический источник для нового правила;
3. меняет только явно разрешённые файлы;
4. не исправляет соседние документы «заодно»;
5. не меняет файлы проекта вне scope активной задачи;
6. не переносит, не удаляет и не переименовывает документы без прямой команды.

Если подходящий документ существует, его обновляют вместо создания дубля.

## 4. Перенос из другого проекта

При переносе документации нужно адаптировать смысл, а не копировать текст вслепую.

Перед завершением проверить, что не перенесены:

- чужое название проекта как действующее;
- чужая архитектура;
- чужие абсолютные пути;
- чужие файлы и каталоги;
- чужая история задач;
- правила технологий, которых нет в текущем проекте;
- локальное состояние редакторов, workspace/session/cache;
- архивные и временные материалы.

Историческое указание источника миграции допустимо, но не превращает его в активный источник правды.

## 5. Новые документы и SplitDoc

Не создавать документы «на будущее» без подтверждённого содержания.

Перед новым файлом ответить:

- какую уникальную задачу он решает;
- почему существующего документа недостаточно;
- кто и когда должен его читать;
- где будет единственный канонический текст правила.

Не плодить SplitDoc без реальной необходимости. Короткое тематическое уточнение добавляется в ближайший существующий документ.

Project_Docs создаются только для подтверждённых сведений конкретного проекта: утверждённой концепции, структуры, сборки, поведения, контрактов и эксплуатационных процедур.

## 6. Формат Markdown

- Один понятный заголовок первого уровня.
- Короткие разделы и обычные списки.
- Настоящие переносы строк, а не текстовая последовательность обратный слэш + n.
- HTML только при реальной необходимости.
- Без автогенерированного мусора.
- Ссылки должны разрешаться из местоположения документа.
- Пути в тексте должны быть переносимыми и относительными корню репозитория.

## 7. Кодировка

Новые и нормализованные Markdown-файлы сохраняются в UTF-8 без BOM.

Русский текст нельзя заменять знаками вопроса, транслитом, символами замены или mojibake. Если текст выглядит повреждённым, сначала проверяется способ чтения и фактические bytes. Неизвестный текст не угадывается.

Полный протокол находится в Documentation_CPP_UE/20_SplitDoc/ENCODING_RULES.md.

## 8. Связи между документами

Если новый документ становится постоянным правилом:

- в START добавляется только короткий маршрут, если правило нужно выбирать при старте;
- в матрицу task-loop добавляется только тематическая строка;
- полный текст остаётся в одном SplitDoc;
- Project_Docs не дублируют общие агентские правила.

## 9. Проверка перед завершением

- Все созданные и изменённые файлы входят в разрешённый scope.
- Нет смысловых дублей.
- Все внутренние Markdown-ссылки разрешаются.
- Нет чужих рабочих путей и предметного контекста.
- Нет машинно-зависимых абсолютных путей как канона.
- Markdown читается нормально.
- Кодировка — UTF-8 без BOM, если задача создаёт или нормализует файл.
- Кириллица не повреждена.
- Нет символа замены U+FFFD и характерных mojibake-фрагментов.
- Нет случайно созданных служебных, временных или editor-state файлов.

## 10. Отчёт

Для документационной задачи указать:

- CREATED FILES;
- CHANGED FILES;
- UPDATED RULES или ADAPTED MECHANISMS;
- CHECKS;
- ENCODING CHECK;
- CHANGED OUTSIDE TARGET или UNEXPECTED CHANGES;
- PROBLEMS;
- CONCLUSION.

Если проектные исходники не менялись, это указывается прямо.

# UNREAL PROJECT RULES

Базовые правила работы со структурой Unreal Engine проекта до и после её фактической инвентаризации.

## 1. Текущее ограничение

На момент TASK 001 Unreal Engine проект ещё не создан. Этот документ не является готовой картой репозитория и не задаёт окончательный `.gitignore`.

После появления проекта нужно сначала выполнить read-only инвентаризацию, затем предложить обоснованную стратегию Git и `.gitignore` отдельным результатом.

## 2. Базовая классификация

- Content/ нельзя автоматически считать мусором: там находятся проектные assets, включая бинарные.
- Source/ обычно содержит авторский исходный код и требует защиты от случайного удаления.
- Config/ содержит настройки проекта; их необходимость и локальность проверяются по фактическим файлам.
- Plugins/ требует индивидуального анализа каждого плагина, его исходников, assets, зависимостей и generated-данных.
- Файл .uproject является важной частью проекта, но его фактическое содержимое должно быть прочитано до выводов об архитектуре.

Эти принципы не подтверждают наличие перечисленных путей в текущем checkout.

## 3. Generated-каталоги

Binaries/, Intermediate/, Saved/, DerivedDataCache/ и другие потенциально generated-каталоги нельзя окончательно классифицировать в рамках bootstrap-документации.

Перед решением нужно проверить:

- фактическую структуру;
- tracked/untracked состояние;
- build и runtime workflow;
- требования команды и используемых плагинов;
- наличие уникальных пользовательских данных;
- возможность безопасного воспроизведения.

Нельзя удалять или добавлять в .gitignore файлы только по названию каталога или общей памяти о типичном Unreal Engine проекте.

## 4. Безопасная работа

1. Сначала инвентаризировать, затем классифицировать.
2. Не удалять и не перемещать файлы без отдельной задачи.
3. Не считать бинарный asset текстом и не пытаться исправлять его кодировку.
4. Не менять .uproject, .uplugin, Config/, Content/, Source/ или Plugins/ вне явного scope.
5. Не создавать окончательный .gitignore без анализа реального проекта.
6. Не считать локальный build-успех доказательством переносимости на другой компьютер.
7. Все спорные файлы оставлять нетронутыми и выносить в вопросы.

## 5. Документирование результата

После инвентаризации подтверждённая карта проекта и build-процесс помещаются в Documentation_CPP_UE/21_Project_Docs/ только при наличии фактических данных. Общие правила остаются в SplitDoc.

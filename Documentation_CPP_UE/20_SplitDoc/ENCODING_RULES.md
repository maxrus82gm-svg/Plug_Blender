# ENCODING RULES

Операционные правила безопасной работы с текстовыми файлами и кириллицей.

## 1. Главный принцип

Русский текст нельзя повреждать. Предпочтительный формат новых и нормализованных текстовых документов — UTF-8 без BOM.

Не считать автоматически, что любой существующий файл уже имеет эту кодировку.

## 2. Когда читать

Документ обязателен при работе с кириллицей и текстовыми форматами, включая:

- .md;
- .txt;
- .json;
- .ini;
- .uproject;
- .uplugin;
- .cs;
- .h;
- .hpp;
- .cpp.

Список не означает, что каждый файл разрешено менять: scope задаёт активная задача.

## 3. Базовые правила

1. Не перекодировать существующий файл без необходимости задачи.
2. Не сохранять файл заново в read-only или аналитической задаче.
3. Перед правкой определить фактическую кодировку, если она не подтверждена.
4. Не угадывать повреждённый русский текст.
5. Не форматировать целый документ ради локальной правки.
6. Делать минимальный патч по стабильному контексту.
7. Сохранять значимые переносы строк, кавычки и спецсимволы.
8. После записи перечитать файл и выполнить подходящие проверки.
9. Не делать массовую перекодировку без отдельной прямой задачи.

## 4. Безопасное чтение и патчи

Некорректный вывод терминала не доказывает порчу файла. Сначала нужно проверить:

- чтение с явным UTF-8;
- первые bytes и наличие BOM;
- декодирование строгим UTF-8;
- наличие символа замены U+FFFD;
- исходный файл, а не уже искажённый вывод.

Для поиска места правки предпочтительны стабильные ASCII-якоря:

- имя класса, функции или переменной;
- ключ JSON;
- секция INI;
- имя модуля;
- техническая константа;
- путь или расширение файла.

Если патч по русской строке не совпал, нельзя расширять замену вслепую. Нужно найти ближайший стабильный якорь и менять минимальный участок.

## 5. Запись

Для новых и нормализованных текстовых документов использовать UTF-8 без BOM.

Инструмент записи должен явно сохранять UTF-8. После записи проверить:

- файл строго декодируется как UTF-8;
- BOM отсутствует, если требуется UTF-8 без BOM;
- кириллица читается нормально;
- переносы строк сохранены;
- не появились повторяющиеся знаки вопроса, символы замены или mojibake.

## 6. Unreal Engine assets

Файлы .uasset и .umap являются бинарными. Их нельзя читать, классифицировать, исправлять или перекодировать как обычный UTF-8 текст.

Другие бинарные assets также не входят в текстовый encoding-процесс. Их формат и допустимый способ изменения определяются отдельно.

## 7. Аварийный протокол

Если русский текст выглядит повреждённым:

1. не перезаписывать файл;
2. локализовать файл и участок;
3. определить, повреждены ли bytes или только вывод;
4. проверить способ чтения и фактическую кодировку;
5. найти надёжный источник корректного текста;
6. если источник неизвестен — остановить эту правку и записать проблему;
7. если восстановление доказуемо — исправить только повреждённый участок;
8. повторить проверки UTF-8, BOM, кириллицы и синтаксиса формата.

Корректным источником может быть подтверждённый текст пользователя, проверенная резервная копия, история задачи или другой достоверный оригинал. Догадка источником не является.

## 8. Проверки по типу файла

Использовать только релевантные доступные проверки:

- JSON parse для .json, .uproject и .uplugin;
- синтаксическая или compile/build-проверка для C++ и .cs, если она входит в задачу;
- проверка секций и ожидаемых значений для .ini;
- проверка внутренних ссылок для Markdown;
- сравнение минимального diff, если Git-review разрешён.

Успешная проверка кодировки не доказывает корректность логики или сборки.

## 9. Отчёт

Если менялись файлы с кириллицей, указать:

- какие файлы проверены;
- как подтверждён UTF-8;
- есть ли BOM;
- нормально ли отображается кириллица;
- были ли признаки реального повреждения;
- выполнялось ли восстановление.

При восстановлении отдельно указать файл, причину, источник корректного текста, способ исправления и проверки после записи.

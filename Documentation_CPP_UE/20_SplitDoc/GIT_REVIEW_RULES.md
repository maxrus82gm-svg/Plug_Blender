# GIT REVIEW RULES

Правила Git, GitHub, diff и review для репозитория PitomecNeyroLokal.

## 1. Канонический репозиторий

- GitHub: maxrus82gm-svg/PitomecNeyroLokal.
- Основная ветка: main.
- Активная документация: Documentation_CPP_UE/.

Локальный абсолютный путь к checkout не является каноническим и может отличаться на разных компьютерах.

## 2. Контроль Git

Git контролирует пользователь.

Без отдельной прямой команды агент не выполняет:

- git add;
- git commit;
- git push;
- git pull;
- git merge;
- git rebase;
- git reset;
- git clean;
- git checkout;
- git switch;
- создание, удаление или переключение веток и тегов;
- изменение remote или Git-конфигурации;
- переписывание истории;
- удаление tracked-файлов из индекса.

Пользовательский запрос на изменение файлов не является автоматическим разрешением на commit или push.

## 3. Read-only Git

Read-only команды допустимы только когда задача связана с Git, diff, status, review или когда такая проверка явно нужна критерию готовности.

Примеры:

- git status --short;
- git branch --show-current;
- git remote -v;
- git log;
- git diff;
- git diff --check;

Если Git использовался, отчёт перечисляет реально выполненные проверки. Эти команды не должны менять рабочие файлы, индекс, ветку, remote или историю.

## 4. Пользовательские изменения

Любые незакоммиченные изменения могут принадлежать пользователю.

Агент:

- не откатывает их;
- не перезаписывает без необходимости текущей задачи;
- не очищает рабочее дерево;
- не смешивает их со своими правками молча;
- сообщает о пересечении со scope или риске.

Если Git не проверялся, нельзя утверждать, что локальных изменений нет.

## 5. GitHub и локальный Git

GitHub содержит только отправленное состояние. Отсутствие изменения на GitHub не доказывает отсутствие локальной правки.

При чтении GitHub указывать:

- repository;
- branch/ref;
- commit SHA и message, если подтверждены;
- ключевые прочитанные файлы;
- полноту проверки.

Неподтверждённые сведения помечаются как неподтверждённые с причиной.

## 6. Review после AGENT REPORT

Если доступны файлы или репозиторий, ChatGPT проверяет фактический результат, а не принимает AGENT REPORT как единственное доказательство.

### REVIEW SOURCE перед содержательной проверкой

До начала содержательного review ChatGPT сначала определяет фактический источник, который собирается проверять, и сразу показывает его пользователю:

```text
REVIEW SOURCE:
- repository: owner/name
- branch/ref: ...
- commit: полный SHA
- commit message: ...
```

При необходимости дополнительно указываются короткий SHA и дата commit. SHA, repository и branch/ref нельзя угадывать. Если какой-либо реквизит достоверно определить невозможно, это сообщается пользователю до review.

Нужно явно различать источники:

1. Если проверяемый remote commit действительно содержит изменения агента, ChatGPT прямо сообщает, что review проводится по этому commit.
2. Если AGENT REPORT относится к локальным незакоммиченным или ещё не отправленным изменениям, ChatGPT показывает доступный remote HEAD и предупреждает, что изменения отчёта этим commit не подтверждаются. Нельзя создавать впечатление, что GitHub-review проверил локальные изменения.
3. Если ChatGPT имеет доступ к локальному checkout и проверяет рабочие файлы или diff, это обозначается отдельно как local review. Его нельзя смешивать с remote GitHub review.
4. Если repository, branch/ref или commit определить невозможно, ограничение показывается до содержательной проверки; недостающий SHA не подставляется предположением.

Порядок review после AGENT REPORT:

1. определить repository;
2. определить branch/ref;
3. определить фактический HEAD/commit доступного источника;
4. сразу показать пользователю REVIEW SOURCE;
5. после этого прочитать необходимые файлы, diff и другие данные;
6. сопоставить AGENT REPORT с фактическим состоянием;
7. не приписывать проверяемому commit изменения, которых в нём нет;
8. выдать результат review.

Review сопоставляет:

- заявленный scope;
- фактически изменённые файлы;
- содержание изменений;
- доступные тесты;
- ограничения проверки;
- состояние commit/push, только если оно реально проверялось.

Если проверка невозможна, причина указывается явно.

## 7. UNEXPECTED CHANGES

При review фактически изменённые файлы сравниваются со scope задачи.

В UNEXPECTED CHANGES перечисляются любые изменения вне scope, включая:

- IDE settings;
- workspace и session state;
- cache и временные файлы;
- локальные файлы редакторов;
- generated-файлы, если их изменение не ожидалось;
- документацию или исходники, не разрешённые задачей.

Обнаруженное изменение не откатывается автоматически. Если оно мешает работе, агент сообщает риск и останавливает конфликтующую часть.

Если diff/status не проверялись, писать: «UNEXPECTED CHANGES не проверялись».

## 8. Служебные файлы

Примеры требующих отдельного внимания:

- .vs/;
- .vscode/;
- локальные workspace/session файлы;
- cache;
- временные файлы;
- пользовательские настройки IDE;
- generated project files.

Конкретная политика .gitignore определяется после анализа фактического Unreal Engine проекта. Этот документ не задаёт окончательный список игнорирования.

## 9. Формат Git-раздела отчёта

Указать только факты:

- ветка и remote, если проверялись;
- status и diff, если проверялись;
- изменялись ли индекс, история или remote;
- создавался ли commit;
- выполнялся ли push;
- проверялся ли GitHub.

Если агент не выполнял commit и push:

- Commit не создавался агентом.
- Push не выполнялся агентом.
- Git-история не изменялась агентом.

## 10. Завершение

Git используется для контроля и анализа только в рамках задачи. После разрешённой проверки или правки агент пишет отчёт и останавливается. Следующее Git-действие не предполагается автоматически.

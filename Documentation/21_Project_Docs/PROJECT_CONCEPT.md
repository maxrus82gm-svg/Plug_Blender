# PROJECT CONCEPT — Plug_Blender

Концепция подтверждена пользователем в TASK 001. Название Blender integration из TASK 003 — Astro Modeler. Широкие modelling-возможности остаются целью будущей системы; текущая реализация отдельно отражена в состоянии проекта (`Documentation/01_Текущее_состояние.md`).

## 1. Назначение проекта

Plug_Blender — AI-помощник для 3D-моделирования в Blender. Он должен ускорять работу 3D-моделлера: помогать создавать правильные болванки, симметричную геометрию, базовые технические формы, повторяющиеся элементы и модели по точным размерам или текстовому описанию.

## 2. Подтверждённая цель

AI должен взаимодействовать с Blender через реальные контролируемые операции над сценой. Результат взаимодействия — создание или изменение геометрии, которую пользователь видит в Blender и может дорабатывать.

## 3. Архитектурное направление

Предпочтительный путь — Codex как клиент/host → наш MCP server → Blender integration → Blender Python API → Blender Scene. В TASK 003 выбран и проверен минимальный локальный механизм для Create Cube; детали прототипа не объявлены окончательной архитектурой продукта.

Обязательное прямое использование OpenAI API из Blender не предполагается. Схема и границы ответственности описаны в архитектуре (`Documentation/04_Архитектура.md`); выбранные принципы — в решениях (`Documentation/02_Решения.md`).

## 4. Первый vertical prototype

Первый технический milestone: **Codex → MCP → Blender → Create Cube**. В TASK 003 установленный Codex app-server обнаружил и дважды вызвал одну контролируемую операцию; реальные кубы подтверждены в открытом Blender Scene. Затем пользователь подтвердил создание Cube в рабочем Blender по команде из обычного текстового Codex и принял TASK 003. Объём проверок — в `Documentation/21_Project_Docs/ASTRO_MODELER_SETUP.md`.

После review Create Cube следующий предлагаемый тест — получить список объектов сцены и определить текущий selected object. Эта работа не выполнялась и запускается отдельной постановкой. Основной интерфейс прототипа — существующий диалог Codex; внутри Blender только служебная панель запуска/остановки и статуса, без чата или prompt field.

## 5. Принцип controlled tools

Основные операции предпочтительно предоставлять модели отдельными контролируемыми инструментами. Ниже только концептуальные примеры, без утверждённых сигнатур или готовой реализации:

- `create_object`, `delete_object` — создание и удаление объекта.
- `get_scene_objects`, `get_selected_object` — чтение сцены и выделения.
- `set_transform`, `add_modifier` — изменение объекта.
- `execute_blender_python` — дополнительный escape hatch для произвольного Python.

Произвольный Python не должен автоматически становиться единственным способом управления Blender. Его ограничения и способ безопасного исполнения ещё предстоит определить.

В перспективе могут появиться high-level modelling tools: `create_radial_array`, `make_symmetric`, `create_from_dimensions`, `create_profile`, `extrude_profile`, `create_bolt_pattern`. Это примеры идей; их подробное проектирование и реализация не входят в bootstrap.

## 6. Роль 3D-моделлера

Цель не требует полной замены специалиста. AI создаёт и изменяет геометрию, ускоряет рутинную работу и подготавливает результат. Пользователь оценивает форму, задаёт требования и продолжает ручную доработку. Возможность дальнейшего редактирования модели человеком — часть желаемого процесса.

## 7. Будущая работа по изображениям и чертежам

В дальнейшем рассматривается построение по изображениям, референсам и чертежам: анализ формы, размеров и соответствия заданию. При нехватке существенных размеров AI сможет уточнять их у пользователя. Формат передачи материалов, масштаб и механизмы анализа пока не выбраны.

## 8. Будущий feedback loop

Желаемый цикл: операция над сценой → viewport/render feedback → анализ результата и сравнение с целью → итерационное исправление модели. Способ получения screenshots, изображений viewport или render и передачи обратной связи ещё не определён.

## 9. Что ещё не решено

Для первого прототипа определены проверенная среда, SDK, transport/IPC, границы процессов, main-thread execution, исходники и минимальная ZIP-установка. Открыты дальнейшая совместимость и production packaging, scene state, undo/transactions, ограничения будущего arbitrary Python, механизмы референсов и feedback, необходимость прямого API в будущих сценариях и конкретный технический режим Astra.

Полный актуальный перечень хранится в открытых вопросах (`Documentation/03_Открытые_вопросы.md`). Эти решения принимаются по результатам исследования и реального прототипа, отдельными проверяемыми этапами. Наличие идеи в концепции не является обязательством roadmap.

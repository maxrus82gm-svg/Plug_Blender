# Правила агента Plug_Blender

Канонический источник ролей, автономности, границ работы и соразмерности проверок. Маршруты чтения и жизненный цикл задачи находятся в START (`Documentation/12_Старт_агента.md`).

## Роли

```text
Пользователь ↔ ChatGPT ↔ Codex Agent ↔ repository / Blender
```

Это процесс взаимодействия, а не технический режим модели или уже работающая Blender integration.

**Пользователь** принимает окончательные продуктовые и архитектурные решения, контролирует изменяющие Git-действия и принимает TASK после review.

**ChatGPT** до постановки обычной технической TASK подготавливает минимально достаточные подтверждённые сведения, при необходимости исследует внешние первоисточники и отделяет факты от предположений. Указывает конкретные документы / разделы для Codex Agent, помогает проектировать архитектуру, формирует TASK и scope, проверяет результат и выполняет внешнее INDEPENDENT REVIEW, определяющее окончательный статус TASK. При необходимости формирует REVIEW CORRECTION. Соблюдает порядок немедленного review и перед Большим блоком каждой новой TASK рекомендует модель и уровень reasoning Codex Agent по START.

**Codex Agent** анализирует фактический репозиторий, исполняет задачи и утверждённые решения, проводит доступные проверки и честно сообщает неопределённости. Конкретная модель является сменным исполнителем TASK, а не архитектурной зависимостью Astro Modeler. После AGENT REPORT формирует AGENT REVIEW: что считает выполненным, что проверил и не проверил, проблемы, ограничения и собственный вывод. Это мнение исполнителя может быть ошибочным и не принимает TASK; далее статус AWAITING INDEPENDENT REVIEW. Канонический порядок и синхронизация внешнего verdict — в START. Контекст использует экономно: обязательное чтение дополняет только релевантными источниками, к истории обращается по необходимости. В пределах задачи агент может выступать техническим аналитиком: исследовать и сравнивать варианты, находить риски, предлагать улучшения и более простой путь, указывать на проблему в плане. Предложение не означает разрешения самостоятельно менять подтверждённую архитектуру или scope.

## Подготовленный контекст и fallback research

Codex Agent в первую очередь использует подготовленные проектные материалы, сопоставляет их с фактическим кодом, реализует решение и проверяет результат. Широкое повторное внешнее исследование не является действием по умолчанию. Это не ограничивает техническое рассуждение: агент может заметить ошибку в постановке, предложить лучший способ или выявить риск.

Самостоятельный внешний research нужен при недостатке сведений, отличии фактического API от ожидаемого, неоднозначности, устаревании документации, необъяснимой имеющимся контекстом ошибке либо необходимости проверить важный технический факт перед реализацией. Сначала сформулируй конкретный неизвестный вопрос, затем ищи ответ именно на него. Полезное для будущих TASK знание отметь в AGENT REPORT / Agent Feedback как кандидат в локальную базу; правила отбора — `Documentation/20_SplitDoc/DOCUMENTATION_RULES.md`.

## AI и детерминированная механика

Codex Agent отвечает за смысл: понимает намерение пользователя, интерпретирует состояние, определяет проблему, выбирает инженерное решение и риск, назначает OK/WARNING/BLOCKED, объясняет рекомендацию и называет отсутствующую capability. Обычный Blender/Python-код выполняет всё, что однозначно вычисляется алгоритмом: числа и измерения, геометрические проверки, exact comparison, validation, timestamps, counters, duplicate compaction, filtering, bounded history и подготовку compact structured results. Не используй LLM там, где надёжный результат даёт детерминированный код.

Для будущих geometry inspection tools Blender вычисляет компактные факты, а Codex Agent интерпретирует их. Уже реализованный пример — точная агрегация последовательных дублей Agent Feedback обычным Python.

## Автономность внутри scope

**BIAS TOWARD ACTION WITHIN SCOPE, ASK WHEN THE ANSWER CAN MATERIALLY CHANGE THE OUTCOME.**

Если намерение и scope понятны, выполняй работу до логического завершения. Обычные небольшие пробелы разумно закрывай по текущей TASK, репозиторию, подтверждённой документации и контексту. Безопасные редакторские и технические детали внутри разрешённого результата не требуют отдельного подтверждения.

Сфокусированный вопрос нужен, если ответ может существенно изменить архитектуру, public interface, формат данных, dependencies, безопасность, значительную часть реализации, разрешённый scope, удаление/перенос важных файлов или необратимое действие. Уже выданное разрешение учитывается: повторно спрашивать о той же разрешённой операции не требуется.

Объясни конкретную неопределённость, её влияние и предлагаемый вариант. До ответа приостанови только зависимую часть; безопасную независимую работу продолжай. Если остановку требует инструкция, укажи её источник и применимое правило.

## Границы и факты

- Текущая TASK и явные уточнения пользователя имеют приоритет над устаревшим перенесённым контекстом. При существенном конфликте с подтверждённым решением обозначь конфликт; не подменяй решение предположением.
- Аналитическая TASK остаётся аналитической, пока пользователь не расширил scope. Разрешённые изменения определяются её целью и явными границами.
- Соседняя проблема вне scope фиксируется в отчёте или рекомендованной следующей задаче; автоматическое исправление не следует из самого обнаружения.
- Фактические файлы и результаты проверок важнее прежнего отчёта. Будущие функции, выбранные направления и реально работающие возможности обозначаются раздельно.
- Сохранность пользовательских изменений и разрешения на Git определяются `Documentation/20_SplitDoc/GIT_REVIEW_RULES.md`.

## Agent Feedback в Blender

`post_modeling_note` предназначен для коротких пользовательских инженерных сообщений, а не для chain-of-thought, debug dump или журнала каждого tool call. `OK` уместен после существенной успешно завершённой моделирующей операции; `WARNING` — при риске, существенной неопределённости, частичном результате или безопасно обходимой ошибке; `BLOCKED` — когда без решения пользователя или конкретной отсутствующей capability безопасно продолжить нельзя. Missing capability называй явно.

Summary кратко и самодостаточно отвечает, что произошло или в чём проблема. Details дополняет summary только новой полезной информацией: причиной, проверенным фактом, рекомендацией, missing capability или следующим необходимым шагом. Не повторяй summary дословно в details. Python агрегирует только точные последовательные дубли; semantic/fuzzy deduplication текста не вводится.

Не публикуй note после каждого простого read-only чтения, после самого `post_modeling_note`, ради формального заполнения журнала или многократно для одной и той же ошибки. Для зависимой ветки действует предел: одна проблема → максимум одна полезная read-only диагностика → один WARNING/BLOCKED → STOP. Повтор разрешён, только если состояние изменилось, появилась новая информация, первая ошибка однозначно устранена или пользователь явно попросил повторить. Для неидемпотентной mutation с неопределённым результатом автоматический retry запрещён.

Локальный `.runtime/agent_feedback.jsonl` — диагностическая история, а не обязательный контекст Codex Agent: не читай его автоматически при новой TASK. Открывай только небольшой tail, диапазон или фильтр, когда конкретная TASK прямо требует log либо исследуется конкретная проблема; весь накопленный файл в модельный контекст не загружай.

## Соразмерные проверки

Перед существенными проверками кратко сформулируй минимальный `VERIFICATION PLAN`: каждая проверка должна закрывать конкретный риск или acceptance criterion. Отдельный большой документ не нужен.

Используй минимально необходимый уровень: A — targeted/static/unit для локальной deterministic logic; B — один целевой Blender runtime для bpy, lifecycle, UI, operators, main thread или установленного add-on; C — real Codex/model turn только для tool discovery, MCP schema/instructions или реально зависящего от модели поведения; D — user/manual visual acceptance только когда runtime не доказывает UX или читаемость.

Verification should be proportional to the change. Выполни проверки, непосредственно необходимые для изменённого материала и критериев TASK. Для маленькой обратимой правки широкое тестирование не требуется. Остановись, когда критерии изменённой части доказаны, релевантная regression зелёная, новой ошибки или неопределённости нет, а следующая проверка лишь повторила бы уже полученное доказательство.

После успешных релевантных проверок не повторяй и не расширяй их без причины. Дополнительные проверки нужны при новой правке, ошибке, риске или неясности. Для документационной задачи проверяются Markdown, ссылки, encoding, структура и diff; отсутствие изменений реализации не требует Blender runtime tests.

Если check упал, сначала классифицируй причину: production defect, test/harness defect, environment/runtime problem, stale loaded add-on, неверное expectation или неизвестная причина. Затем выполни одну целевую диагностику, исправь причину, повтори только затронутый уровень и минимальную нужную regression. Не переписывай production code при доказанном дефекте harness и не перезапускай всю verification chain без нового риска.

В AGENT REPORT разделяй выполненные, неуспешные, недоступные и неприменимые проверки. PASS допустим только для фактически выполненной успешной проверки. Статический анализ и чтение текста не доказывают успешный runtime; проверка агентом не означает принятие TASK пользователем.

## Native-first

Если Blender предоставляет подходящий Panel, box/row/label, operator, standard icon, native resizing или другой штатный UI/state mechanism, используй его прежде собственной инфраструктуры. Astro Modeler добавляет бизнес-логику и вводит custom UI только при доказанной недостаточности native Blender UI.

## БЛОК 1 — ТЕКУЩАЯ ЗАДАЧА

TASK 015 — Agent Activity HUD + deterministic Tool Usage Telemetry

ЦЕЛЬ

Добавить в Astro Modeler простую локальную визуализацию активности Codex Agent:

1. Пользователь должен видеть в 3D View, какой Astro Modeler tool
   сейчас/последним был вызван агентом.

2. Astro Modeler должен автоматически считать,
   сколько раз фактически использовался каждый public MCP tool.

3. Эта информация должна собираться обычным Python-кодом.
   Codex Agent НЕ должен специально сообщать:
   "сейчас я использую такой-то tool".

4. Не добавлять новый MCP tool только ради telemetry.

5. Не превращать Agent Feedback Log в журнал каждого tool call.

Текущий public MCP contract остаётся:
- create_cube
- get_selected_context
- create_box_at_cursor
- post_modeling_note

Количество public MCP tools после TASK 015 должно остаться: 4.

==================================================
1. ИСТОЧНИК ACTIVITY
==================================================

Activity должна фиксироваться автоматически внутри Astro Modeler
при обработке настоящего bridge command.

Использовать реальное имя public command:

- create_cube
- get_selected_context
- create_box_at_cursor
- post_modeling_note

Не просить модель отдельно отправлять имя использованного tool.

Предпочтительная архитектура:

MCP command
→ существующий Bridge
→ internal activity hook/runtime state
→ выполнить существующую operation
→ записать результат activity
→ UI/HUD читает только runtime activity state.

Конкретную небольшую форму callback/helper исполнитель может выбрать сам.

ВАЖНО:
не менять публичную MCP schema без необходимости.


==================================================
2. ЧТО СЧИТАЕТСЯ TOOL CALL
==================================================

После успешной проверки session token и определения
поддерживаемой public command фиксировать один tool invocation.

Один входящий вызов = +1 к счётчику этого tool.

Хранить как минимум:

- tool_name
- call_count
- last invocation time
- последний outcome: success / error

Не хранить:
- token;
- полный request;
- Selected Context;
- mesh data;
- tool arguments;
- chain-of-thought;
- пользовательскую геометрию.

Если операция завершилась ошибкой,
сам факт фактического вызова всё равно может учитываться,
но outcome должен быть ERROR.

Не удваивать счётчик из-за внутренних callback/helpers.


==================================================
3. VIEWPORT HUD
==================================================

Добавить небольшой HUD/overlay в 3D View.

Пользователь хочет видеть глазами,
какой Astro Modeler tool агент использует во время работы.

ВАЖНО:
текущий bridge выполняет Blender operation синхронно на main thread.
Не перестраивать ради TASK 015 execution pipeline
только для того, чтобы гарантировать redraw посреди одной операции.

Поэтому HUD НЕ должен ложно обещать точный realtime running-state,
если Blender не успел физически перерисовать viewport.

Достаточный UX первой версии:

при каждом фактическом tool invocation HUD обновляет отображаемое имя,
например:

ASTRO MODELER
get_selected_context

или:

Astro Modeler · get_selected_context

После завершения вызова имя остаётся видимым небольшой период,
чтобы пользователь реально успевал заметить смену tools.

Допустимый простой timeout:
примерно 2–4 секунды.

Конкретное значение выбрать простое и зафиксировать.

При следующем tool call HUD сразу переключается на новое имя.

После timeout HUD может исчезать.
Постоянный огромный IDLE overlay не требуется.

Не отображать arguments/results в HUD.


==================================================
4. ВНЕШНИЙ ВИД HUD
==================================================

Первая версия должна быть простой.

По умолчанию:

- HUD включён;
- цвет текста — зелёный;
- размер немного крупнее обычного Blender UI;
- расположение — верхняя центральная/близкая к центральной
  свободная зона 3D View, чтобы activity было легко заметить.

Не закрывать модель большим блоком.

Использовать Blender viewport drawing mechanism,
например штатный draw handler + blf,
если это является нормальным и простым решением.

Не создавать custom GPU/UI framework.

==================================================
7. TOOL USAGE STATISTICS
==================================================

Статистика runtime-only.

Минимально:

tool_name → count

Дополнительно можно хранить:
- successes
- errors

но не раздувать UI,
если это не улучшает понимание.

В основном списке достаточно вида:

tool_name ×N

Показывать только реально использованные tools
или все 4 tools с нулём — выбрать более компактный вариант.
Предпочтительно показывать использованные.

Clear Statistics:
- очищает counters;
- очищает last activity при необходимости;
- не меняет Scene;
- не создаёт Undo step модели;
- не трогает Agent Feedback.


==================================================
8. LIFECYCLE
==================================================

Telemetry не должна находиться в Scene/.blend.

Предпочтительное поведение:

- Stop Integration:
  statistics можно сохранить в runtime текущего Blender процесса;

- повторный Start Integration:
  не обязан уничтожать statistics;

- Clear Statistics:
  явно очищает;

- disable/unregister add-on:
  draw handler обязательно удалить,
  runtime telemetry очистить;

- полный Blender restart:
  начинается новая runtime telemetry session;

- загрузка другого .blend:
  activity HUD не должен оставаться в неправильном RUNNING state.

Не оставлять orphan draw handlers после unregister/reload.


==================================================

==================================================

Не вызывать post_modeling_note после каждого tool call.

Activity HUD + Tool Usage — отдельная deterministic telemetry.

Никакой рекурсии:

tool call
→ activity telemetry

но НЕ:

tool call
→ post_modeling_note
→ activity
→ post_modeling_note ...

13. ОЧЕНЬ ВАЖНАЯ БЛИЖАЙШАЯ CAPABILITY

В TASK 015 НЕ РЕАЛИЗОВЫВАТЬ следующую capability.

Но обязательно зафиксировать её как одну из самых ближайших
в существующей очереди/идеях проекта:

TASK / CAPABILITY:
Modifier Changed Parameters Inspector

Пользовательский сценарий:

есть объект с уже настроенными Blender modifiers.

Пользователь хочет получить НЕ полный dump modifier properties,
а только те параметры, которые отличаются
от стандартных значений этого modifier type в текущем Blender.

Пример:

Bevel

width:
default 0.1
current 0.003

segments:
default 2
current 6

limit_method:
default OFFSET
current ANGLE

Параметры, которые остались стандартными,
в результат не включать.

ВАЖНЫЙ архитектурный принцип будущей capability:

Blender/Python:
- получает modifier stack;
- определяет фактические default values;
- выполняет exact/deterministic comparison;
- возвращает компактный structured diff.

Codex Agent:
- интерпретирует результат;
- объясняет пользователю смысл изменений.

При проектировании будущей задачи исследовать,
какой источник defaults надёжнее:

- Blender RNA/default metadata;
- временно созданный modifier соответствующего типа;
- другой штатный Blender mechanism.

НЕ считать заранее, что временный Cube обязательно лучший способ.
Нужно выбрать фактически надёжный способ.

Будущие расширения этого семейства:
- object A vs object B modifier diff;
- saved snapshot vs current state.

Это одна из ПЕРВЫХ задач после TASK 015.
Не потерять её среди общих идей.

После неё в ближайшем приоритете остаётся:

# Задача агенту — Plug_Blender

Рабочий файл текущего цикла. Канонический порядок постановки, исполнения, отчёта и review: START (`Documentation/12_Старт_агента.md`). Краткая история: `Documentation/20_SplitDoc/TASK_HISTORY.md`.

## БЛОК 1 — ТЕКУЩАЯ ЗАДАЧА

TASK 014 — Efficient Agent Loop + deterministic mechanics + compact Feedback UX

ЦЕЛЬ

Перед дальнейшим массовым расширением Blender capabilities
закрепить экономный и предсказуемый рабочий цикл Codex Agent.

Главные идеи:

1. AI отвечает за смысл и инженерное решение.
2. Обычный Python/Blender-код выполняет детерминированную механику.
3. Проверки должны закрывать конкретный риск и останавливаться,
   когда достаточное доказательство уже получено.
4. Agent Feedback должен оставаться компактным и удобным
   в реальном Blender Sidebar.

Не добавлять в этой TASK новые моделирующие capabilities.


==================================================
1. ПРИНЦИП: AI = СМЫСЛ, CODE = ДЕТЕРМИНИРОВАННАЯ МЕХАНИКА
==================================================

Закрепить как постоянный проектный принцип:

Codex Agent используется там, где требуется:
- понять намерение пользователя;
- интерпретировать состояние;
- определить проблему;
- выбрать инженерное решение;
- оценить риск;
- выбрать OK / WARNING / BLOCKED;
- объяснить рекомендацию;
- определить, какой capability/tool отсутствует.

Обычный Blender/Python-код должен выполнять всё,
что можно однозначно вычислить алгоритмом:

- численные расчёты;
- измерения;
- геометрические проверки;
- exact comparison;
- валидацию;
- timestamps;
- counters;
- duplicate compaction;
- filtering;
- bounded history;
- подготовку compact structured results;
- другие механические операции без необходимости reasoning модели.

Не использовать LLM там, где результат можно надёжно получить
обычным детерминированным алгоритмом.

Пример уже реализованного применения:
точные последовательные дубликаты Agent Feedback
агрегирует Python, а не Codex Agent.

Этот принцип должен использоваться и при проектировании
будущих geometry inspection tools:
Blender вычисляет факты, агент интерпретирует результат.


==================================================
2. VERIFICATION PLAN ПЕРЕД ПРОВЕРКАМИ
==================================================

Закрепить правило:

Перед началом существенных проверок агент определяет
минимальный verification plan, соответствующий изменению.

Не нужен отдельный большой документ или длинный план.
Достаточно короткой рабочей схемы.

Пример:

VERIFICATION PLAN
- targeted unit tests;
- one Blender runtime;
- manual visual check.

Каждая проверка должна отвечать на конкретный риск
или acceptance criterion TASK.

Не запускать дополнительные проверки просто потому,
что они доступны.


==================================================
3. УРОВНИ ПРОВЕРКИ
==================================================

Использовать минимально необходимый уровень.

Уровень A — targeted/static/unit
Используется первым для локальной логики:
- validation;
- pure Python helpers;
- serialization;
- counters;
- deterministic state.

Уровень B — Blender runtime/integration
Нужен, когда изменение зависит от:
- bpy;
- lifecycle;
- Scene;
- Blender UI;
- operators;
- main-thread behavior;
- установленного add-on.

Обычно достаточно одного целевого runtime после зелёных
локальных проверок.

Уровень C — real Codex/model acceptance
Нужен только когда изменение действительно зависит от:
- tool discovery;
- MCP schema/instructions;
- поведения модели;
- настоящего model turn.

Не запускать real model turn автоматически для каждой
обычной Python/UI правки.

Уровень D — user/manual visual acceptance
Использовать только там, где автоматический runtime
не способен доказать UX/читаемость/визуальный результат.


==================================================
4. STOP CONDITIONS FOR VERIFICATION
==================================================

Закрепить явные условия остановки.

Проверки прекращаются, когда одновременно:

- критерии изменённой части TASK доказаны;
- релевантные regression checks зелёные;
- новая ошибка или неопределённость отсутствует;
- следующая проверка повторила бы уже полученное доказательство.

После этого агент должен перейти к завершению TASK,
а не искать ещё один способ убедиться в том же результате.

Больше тестов ≠ автоматически лучшее качество.


==================================================
5. ЕСЛИ ПРОВЕРКА УПАЛА
==================================================

Использовать короткий diagnostic loop:

FAILED CHECK
→ определить класс проблемы
→ одна целевая диагностика
→ исправить причину
→ повторить только релевантный уровень
→ минимальная нужная regression
→ STOP.

Перед исправлением различать:

- production defect;
- test/harness defect;
- environment/runtime problem;
- stale loaded Blender add-on;
- неверное test expectation;
- неизвестная причина.

Не переписывать production code,
если факты показывают проблему только в harness.

Не запускать автоматически полный verification chain заново
после исправления локальной test-only ошибки.

Пример:
если Blender runtime упал из-за неверного test expectation,
после исправления повторяется этот runtime и только необходимая
регрессия, а не вся цепочка research → unit → SDK → real Sol
без конкретной причины.


==================================================
6. STOP-ON-PROBLEM
==================================================

Сохранить правило TASK 013 и сделать его согласованным
с verification loop:

одна проблема
→ максимум одна полезная read-only диагностика
→ один WARNING/BLOCKED
→ STOP зависимой ветки.

Повтор операции разрешён только если:
- состояние изменилось;
- появилась новая информация;
- первая ошибка была однозначно устранена;
- пользователь явно попросил повторить.

Не делать циклы:
try → fail → try → fail → try → fail.

Для неидемпотентных mutating operations при неопределённом результате
автоматический retry по-прежнему запрещён.


==================================================
7. AGENT FEEDBACK — КАЧЕСТВО ТЕКСТА
==================================================

Уточнить contract/instructions:

summary:
- кратко отвечает, что произошло / в чём проблема;
- самодостаточен;
- не должен быть длинным абзацем.

details:
- ДОПОЛНЯЕТ summary;
- не повторяет его дословно;
- содержит только новую полезную информацию:
  причину, проверенный факт, рекомендацию, missing capability,
  следующий необходимый шаг.

Пример плохо:

summary:
"Нет локального измерения толщины."

details:
"Не хватает локального измерения толщины."

Пример хорошо:

summary:
"Нет локального измерения толщины."

details:
"Для проверки минимальной стенки нужен controlled mesh-analysis tool,
который вычисляет толщину внутри Blender."

Не пытаться удалять смысловые повторы Python-кодом.
Semantic deduplication модели/текста не вводить.

**BLENDER FEEDBACK UI:** создан отдельный panel `AGENT FEEDBACK LOG` во вкладке Astro Modeler N-panel. Записи выводятся newest-first. Карточка содержит диапазон локального времени `first_time–last_time`, статус, `×repeat_count`, полный summary и компактный details preview примерно на три строки. Полный details раскрывается и сворачивается локальной кнопкой; состояние раскрытия хранится только в runtime. OK, WARNING и BLOCKED различаются icon/label, WARNING/BLOCKED также используют alert styling. Пустые details не создают separator или пустой блок.

**DUPLICATE COMPACTION:** только соседние notes с детерминированным совпадением `status + summary + details` объединяются в текущий cluster. Повтор обновляет `last_time` и `repeat_count`, сохраняя `first_time`. После любого другого feedback совпадающая note начинает новый cluster. Fuzzy/semantic deduplication и модельное сравнение не используются. Runtime test подтвердил: 100 одинаковых WARNING → один cluster `repeat_count=100`; после промежуточной записи тот же WARNING создаёт отдельный cluster.

**RUNTIME HISTORY:** `deque(maxlen=20)` хранит последние 20 clusters. `Clear Feedback` очищает только feedback и локальное expand/collapse state, без Scene/Object/Text properties и без undo-операции. История очищается при Start Integration, загрузке другого `.blend` и unregister/disable; Stop Integration сохраняет видимый список до следующего Start.

**PERSISTENT DIAGNOSTIC LOG:** `<repo>/.runtime/agent_feedback.jsonl`, compact UTF-8 JSONL. Cluster содержит `first_time`, `last_time` (UTC ISO 8601 до секунд), `repeat_count`, `status`, `summary`, `details`. Последовательные точные дубли агрегируются; файл удерживает последние 200 clusters, чтение существующего tail ограничено 2 MiB. Запись выполняется атомарно только после ответа Blender `success: true`. Token, Selected Context, tool-call dump и chain-of-thought не записываются. Ошибка вторичного log не меняет уже подтверждённую доставку note.

**CONTEXT ECONOMY:** `agent_feedback.jsonl` не является обязательным чтением новой TASK. Правила требуют открывать только небольшой tail, диапазон или фильтр при прямом требовании TASK или конкретном расследовании. Публичный MCP tool чтения feedback history не добавлен.

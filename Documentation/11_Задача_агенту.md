## БЛОК 1 — ТЕКУЩАЯ ЗАДАЧА

TASK 016 — Modifier Changed Parameters Inspector
Blender Defaults Diff + Human Explanation

СТАТУС

ПОДГОТОВЛЕНА ЗАРАНЕЕ.
НЕ ЗАПУСКАТЬ ДО ЗАВЕРШЕНИЯ TASK 015 И INDEPENDENT REVIEW.

Эта TASK является одной из ближайших приоритетных capabilities Astro Modeler.


==================================================
ЦЕЛЬ
==================================================

Сделать первый полезный inspection-инструмент для Blender modifiers.

Пользователь выбирает объект с уже настроенными модификаторами
и хочет быстро узнать:

1. какие параметры модификаторов были изменены
   относительно стандартных значений Blender;

2. какие значения были стандартными;

3. какие значения установлены сейчас;

4. что эти изменения означают человеческим языком;

5. зачем автор модели, вероятно, мог изменить именно эти параметры.


Главный принцип:

PYTHON / BLENDER
→ точно определяет факты и изменения.

CODEX AGENT
→ объясняет смысл найденных изменений.

Не заставлять LLM самостоятельно сравнивать огромные dumps
modifier properties.


==================================================
1. ОСНОВНОЙ USER FLOW
==================================================

Первая версия должна работать максимально просто.

Основной сценарий:

1. Пользователь выбирает один объект в Blender.

2. В Astro Modeler запускается анализ его modifier stack.

3. Blender/Python получает каждый modifier.

4. Для каждого modifier определяется стандартное состояние
   соответствующего modifier type в текущей версии Blender.

5. Текущие значения сравниваются с default values.

6. Параметры, которые НЕ изменены,
   в результат не включаются.

7. Возвращается только compact diff.

8. Codex Agent получает compact structured result
   и объясняет пользователю найденные изменения.


Пример пользовательского результата:

BEVEL

Width
Default: 0.1
Current: 0.003

Segments
Default: 2
Current: 6

Limit Method
Default: OFFSET
Current: ANGLE


Далее Codex Agent может объяснить:

- Width уменьшен — фаска сделана значительно уже;
- Segments увеличены — скругление стало плавнее;
- Limit Method изменён — способ определения обрабатываемых рёбер
  отличается от стандартного.

Не выдавать пользователю сотни неизменённых properties.


==================================================
2. ОТКУДА БРАТЬ BLENDER DEFAULT VALUES
==================================================

Это ключевой технический вопрос TASK.

НЕ создавать вручную огромную таблицу defaults.

Перед реализацией определить наиболее надёжный штатный способ
получить defaults именно из фактического Blender.

Исследовать в первую очередь:

A. Blender RNA property metadata / default values;

B. временное создание modifier соответствующего type
   на безопасном временном объекте;

C. другой штатный Blender mechanism,
   если он объективно надёжнее.

Не считать заранее,
что временный Cube обязательно является правильным решением.

Предпочесть решение, которое:

- использует реальные defaults текущего Blender;
- минимально зависит от hardcoded таблиц;
- не оставляет мусор в пользовательской Scene;
- не портит selection;
- не меняет пользовательский объект;
- не делает .blend dirty без необходимости;
- стабильно работает для поддерживаемых modifier types.


==================================================
3. ЧТО СРАВНИВАТЬ
==================================================

Не пытаться без разбора сравнивать вообще каждое RNA property.

Нужно определить controlled набор сравнимых пользовательских settings.

Учитывать, что Blender modifier может содержать:

- numeric properties;
- bool;
- enum;
- vectors;
- object/collection references;
- strings;
- служебные/internal/read-only properties;
- runtime/internal state.

В результат НЕ должны попадать технические свойства,
которые пользователь не воспринимает как настройку modifier.

Read-only/internal/RNA metadata исключать.

Для floating point сравнения не придумывать fuzzy tolerance
без причины.

Если Blender хранит property так,
что exact representation технически отличается,
но пользовательское значение эквивалентно,
нужно выбрать корректное deterministic comparison rule
и документировать его.


==================================================
4. STRUCTURED RESULT
==================================================

Не отдавать модели полный modifier dump.

Нужен компактный structured result.

Примерная форма:

{
  "object_name": "Body",
  "modifiers": [
    {
      "name": "Bevel",
      "type": "BEVEL",
      "changed_properties": [
        {
          "property": "width",
          "default": 0.1,
          "current": 0.003
        },
        {
          "property": "segments",
          "default": 2,
          "current": 6
        }
      ]
    }
  ]
}

Exact schema исполнитель может уточнить,
но сохранять принцип:

ONLY MEANINGFUL CHANGES.

Если modifier не имеет изменённых пользовательских properties,
не раздувать ответ пустыми данными.


==================================================
5. HUMAN EXPLANATION — ЗДЕСЬ НУЖНА НЕЙРОСЕТЬ
==================================================

Это важная часть продукта.

Python отвечает только на вопрос:

"ЧТО ИЗМЕНЕНО?"

Codex Agent отвечает на вопросы:

- что делает этот параметр;
- на что влияет изменение;
- чем текущее значение отличается по смыслу от default;
- зачем моделлер мог так настроить modifier;
- какое визуальное/техническое последствие это обычно даёт.

ВАЖНО:

Не выдавать предположение о намерении автора как доказанный факт.

Формулировать честно:

"Вероятно..."
"Обычно это делают, чтобы..."
"Такое значение может использоваться для..."

Если назначение однозначно следует из Blender behavior,
можно объяснять увереннее.

Если причина выбора конкретного значения неизвестна,
так и говорить.


==================================================
6. ОБУЧАЮЩИЙ СЦЕНАРИЙ
==================================================

Capability должна быть удобна не только опытному моделлеру,
но и начинающему человеку / ребёнку.

Пример:

Пользователь открывает чужую или свою старую модель,
видит настроенный modifier,
но не понимает, почему значения отличаются от стандартных.

Astro Modeler должен позволить получить:

1. список реально изменённых настроек;

2. простое объяснение каждой настройки;

3. возможную причину изменения;

4. связь настройки с видимым результатом модели.

Это одна из ключевых продуктовых идей TASK 016.


==================================================
7. USER CONTEXT / ИНСТРУКЦИЯ ДЛЯ ОБЪЯСНЕНИЯ
==================================================

В UI предусмотреть небольшой пользовательский контекст
для объяснения результата.

Пользователь должен иметь возможность уточнить,
КАК он хочет разобрать найденные изменения.

Примеры:

"Объясни максимально просто, я только учусь Blender."

"Объясни как ребёнку."

"Меня интересуют только параметры,
которые влияют на подготовку к 3D-печати."

"Объясни, как эти изменения влияют на внешний вид."

"Мне важна производительность viewport."


Не делать из этого огромный prompt editor.

Достаточно небольшого editable text/context field,
если это разумно реализуется в текущем UI.


==================================================
8. БАЗОВЫЙ КОНТЕКСТ + USER OVERRIDE
==================================================

Astro Modeler может иметь короткую стандартную инструкцию
для интерпретации modifier diff.

Например:

"Объясни назначение изменённых параметров,
их влияние и вероятную причину изменения.
Не выдавай предположение о намерении автора за факт."

Пользовательский context ДОПОЛНЯЕТ эту инструкцию,
а не требует переписывать весь system behavior.

Не хранить огромные описания каждого modifier/property
вручную внутри add-on,
если модель уже способна объяснить общеизвестный Blender concept.

Детерминированные FACTS хранятся/вычисляются Python.
Объяснение выполняет модель.

==================================================
11. ПУБЛИЧНЫЙ TOOL
==================================================

TASK 016, вероятно, потребует новый controlled inspection MCP tool.

Рабочая идея имени:

inspect_modifier_changes()

или другое ясное имя.

Перед утверждением проверить consistency
с текущим naming Astro Modeler.

Tool должен:

- работать read-only относительно пользовательской модели;
- анализировать active/selected object;
- возвращать compact diff;
- не возвращать полный arbitrary RNA dump;
- не выполнять arbitrary Python;
- не менять modifiers;
- не применять modifiers;
- не создавать пользовательскую геометрию.

Если для получения defaults используется временное состояние,
оно должно быть полностью служебным и безопасно очищаться.


==================================================
12. ERROR / LIMITATION BEHAVIOR
==================================================

Корректно обработать:

- нет selected/active object;
- active object не поддерживает modifiers;
- modifier type невозможно надёжно сравнить;
- property содержит неподдерживаемый тип;
- object/collection reference;
- read-only/internal properties;
- Blender API неожиданно отличается.

Не падать из-за одного неподдерживаемого property,
если остальные можно безопасно проанализировать.

Но и не скрывать существенную неполноту.

Structured result должен уметь сообщить limitations.


==================================================
13. НЕ ДЕЛАТЬ
==================================================

В первой TASK 016 НЕ делать автоматически:

- object A vs object B;
- snapshot vs current;
- историю изменений;
- automatic restore;
- copy modifier;
- изменение modifier values;
- Apply Modifier;
- arbitrary Python;
- geometry thickness;

==================================================
14. БУДУЩЕЕ РАСШИРЕНИЕ
==================================================

Архитектуру не блокировать для будущих вариантов:

A. CURRENT vs BLENDER DEFAULTS

B. OBJECT A vs OBJECT B

C. SNAPSHOT vs CURRENT

     затем показать, что пользователь изменил.

В TASK 016 реализовать только A,
если пользователь отдельно не расширит scope.


==================================================
15. СВЯЗЬ С TASK 014
==================================================

Строго сохранить принцип:

AI = meaning.
CODE = deterministic mechanics.

Python/Blender:

- определяет modifier;
- получает default;
- сравнивает;
- фильтрует;
- сериализует compact diff.

Codex Agent:

- объясняет;
- обучает;
- связывает изменения с вероятным результатом;
- учитывает user context.

Не тратить model context
на mechanical comparison.


==================================================
16. RESEARCH ПЕРЕД РЕАЛИЗАЦИЕЙ
==================================================

Перед кодом сделать короткий targeted research.

Нужно ответить только на конкретные вопросы:

1. Как наиболее надёжно получить default RNA/property value

2. Какие modifier properties должны быть исключены

3. Есть ли modifier-specific свойства,

4. Как безопасно сериализовать object/collection references?

Не начинать широкий research всего Blender API.

Если официальной документации недостаточно,
разрешён небольшой runtime probe в Blender.


==================================================
17. VERIFICATION PLAN
==================================================

TASK должна использовать экономный verification loop.

LEVEL A

Проверить deterministic diff:

- default == current → property отсутствует в diff;
- default != current → property присутствует;
- bool;
- enum;
- float;
- int;
- vector при наличии;
- excluded/internal properties;
- unsupported property.

LEVEL B

Один targeted Blender runtime:

- создать простой тестовый объект;
- добавить один понятный modifier;
- получить initial defaults;
- изменить 2–3 параметра;
- inspector должен вернуть только эти изменения;
- пользовательский объект не изменён анализом;
- временные test/default objects/datablocks не остаются;
- selection/context не портятся.

Для первого acceptance достаточно,
например, Bevel или другого простого modifier.

После доказательства generic mechanism
не тестировать десятки modifier types без нового риска.


LEVEL C — REAL MODEL

Для TASK 016 real model turn НУЖЕН,
потому что продуктовая ценность включает
интерпретацию structured diff человеком.

Но сделать один короткий acceptance turn:

- получить реальный compact modifier diff;
- попросить Codex Agent объяснить его простым русским языком;
- проверить, что модель не придумывает параметры,
  которых нет в structured result;
- проверить разделение facts и вероятных причин.

LEVEL D

Пользователь вручную оценивает:

- удобно ли запускать анализ;
- понятен ли список;
- полезно ли человеческое объяснение;
- не перегружен ли интерфейс.

После этого STOP.

КРИТЕРИЙ ГОТОВНОСТИ
==================================================

TASK считается технически успешной,
если на выбранном тестовом объекте:

1. Blender/Python надёжно получает modifier defaults;

2. после изменения нескольких settings
   возвращаются именно изменённые properties;

3. неизменённые properties не засоряют result;

4. анализ read-only для пользовательского объекта;

5. Codex Agent получает compact diff;

6. Codex Agent понятно объясняет по-русски,
   что делают найденные параметры;

7. вероятная причина изменения отделяется
   от доказанного факта;

8. пользователь может добавить небольшой context
   для характера объяснения.

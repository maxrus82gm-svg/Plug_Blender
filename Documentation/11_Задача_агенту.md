==================================================
ЦЕЛЬ
==================================================

Сделать удобный инструмент разбора Blender modifiers.

Пользователь должен иметь возможность:

1. выбрать объект;
2. получить список его modifiers;
3. выбрать конкретный modifier;
4. нажать кнопку сравнения;
5. БЕЗ НЕЙРОСЕТИ получить точный список параметров,
   которые отличаются от стандартного freshly-created
   modifier того же типа в текущем Blender;
6. при желании отдельно попросить AI объяснить,
   что означают найденные изменения и зачем их могли сделать.


Главное разделение:

PYTHON / BLENDER:
"ЧТО ИЗМЕНЕНО?"

AI:
"ЧТО ЭТО ЗНАЧИТ И ЗАЧЕМ ЭТО МОГЛИ ИЗМЕНИТЬ?"


==================================================
1. ОСНОВНОЙ USER FLOW
==================================================

V1 должна выглядеть примерно так:

1. Пользователь выделяет объект в Blender.

2. Открывает:

N → Astro Modeler → MODIFIER INSPECTOR

3. Нажимает:

[ Get Modifiers ]

4. Astro Modeler показывает modifiers выбранного объекта.

Например:

Object: Body

Modifier:
[ #1 Mirror       ▼ ]
[ #2 Bevel        ]
[ #3 Solidify     ]
[ #4 Subdivision  ]

5. Пользователь выбирает ОДИН modifier.

Например:

#2 · Bevel · BEVEL

6. Нажимает:

[ Compare Parameters ]

7. Blender/Python самостоятельно:
- читает current modifier;
- создаёт freshly-created reference modifier того же type;
- сравнивает;
- удаляет reference/temp data;
- показывает только различия.

НИКАКАЯ НЕЙРОСЕТЬ ДЛЯ ЭТОГО ШАГА НЕ НУЖНА.


==================================================
2. ЧТО ПОКАЗЫВАЕТ COMPARE PARAMETERS
==================================================

Результат должен отображаться прямо
в MODIFIER INSPECTOR Blender UI.

Например:

BEVEL — Bevel

Changed parameters: 3

Width
Default: 0.100
Current: 0.003

Segments
Default: 2
Current: 6

Limit Method
Default: OFFSET
Current: ANGLE


Если изменений нет:

No changed parameters.
Modifier matches freshly-created Blender defaults.


НЕ показывать сотни неизменённых properties.


==================================================
3. ЭТАЛОН — ИМЕННО ТЕКУЩИЙ BLENDER
==================================================

Research уже доказал:

RNA Property.default/default_array
не всегда соответствует реальному состоянию
freshly-created modifier.

modifier.is_property_set()
тоже не подходит для определения отличий.

Поэтому эталон:

FRESH MODIFIER,
СОЗДАННЫЙ ЭТИМ ЖЕ RUNNING BLENDER.

Это критично.

Пользователь может одновременно иметь:
- Blender 4.x;
- Blender 5.x;
- другие версии;
- различные реализации modifier;
- различные add-ons.

Не использовать другой Blender process
как основной reference source.

Не использовать вручную захардкоженную таблицу defaults.


==================================================
4. TEMP PROBE
==================================================

Для получения reference разрешено
создать временный служебный Object/Modifier
в текущем Blender.

Предпочтительно использовать явно служебную зону:

__ASTRO_MODELER_TEMP__

или аналогичный однозначный prefix.

Допустимо:
- temporary Collection;
- temporary Mesh;
- temporary Object;
- freshly-created modifier.


После анализа удалить всё,
что создала именно эта operation.

Cleanup должен идти через finally-equivalent path.


==================================================
5. DIRTY .BLEND
==================================================

Известное ограничение V1:

создание/удаление temporary datablocks
может отметить .blend как изменённый.

Для V1 это ДОПУСТИМО.

Не пытаться:
- молча Save;
- сбрасывать dirty flag неподтверждённым способом;
- скрывать limitation.

Правильность modifier defaults важнее этого ограничения.

Пользователь знает о поведении.


==================================================
6. TEMP OBJECT НЕ ОБЯЗАН БЫТЬ ВИДИМЫМ CUBE
==================================================

Пользовательская концепция:

"создать кубик и навесить чистый modifier".

Но implementation не обязан использовать bpy.ops cube,
если data API безопаснее.

Предпочтительно, если возможно:

bpy.data.meshes.new
bpy.data.objects.new
obj.modifiers.new

чтобы:
- не сбивать selection;
- не переключать active object;
- не требовать лишнего context.

Главное:
reference modifier действительно создаётся Blender,
а не эмулируется таблицей.


==================================================
7. OBJECT MODE
==================================================

V1 работает только в Object Mode.

Если пользователь находится в неподходящем mode:

не переключать его молча.

Показать понятное сообщение:

Switch to Object Mode before modifier inspection.


==================================================
8. ВЫБОР MODIFIER
==================================================

Не пытаться считывать,
какой modifier визуально активен
в стандартной Blender Properties panel.

Astro Modeler имеет собственный список.

Это специально выбранная архитектура V1.


Идентифицировать modifier не только по type.

На объекте могут быть:

Bevel
Bevel.001
Bevel.002

Хранить как минимум:
- object identity;
- modifier stack index;
- modifier name;
- modifier type.


Если после Get Modifiers пользователь:
- удалил modifier;
- поменял stack;
- переименовал его;
- сменил object;

старый target не должен молча использоваться.

Вернуть stale selection
и предложить Get Modifiers ещё раз.


==================================================
9. COMPARE PARAMETERS — ПОЛНОСТЬЮ ЛОКАЛЬНАЯ ФУНКЦИЯ
==================================================

Кнопка:

[ Compare Parameters ]

НЕ вызывает LLM.

НЕ требует Codex Agent.

НЕ требует пользовательского prompt.

НЕ отправляет данные в conversation.

Она выполняется обычным Blender/Python-кодом.


Это важное продуктовое свойство:

Modifier Inspector полезен,
даже если AI вообще сейчас не используется.


==================================================
10. PROPERTY COMPARISON
==================================================

Сравнивать только meaningful user-facing settings.

Исключать:
- readonly;
- hidden;
- internal;
- RNA metadata;
- methods;
- runtime technical state;
- очевидно служебные properties.

Учитывать:
- bool;
- int;
- float;
- enum;
- string;
- vectors/arrays;
- Blender datablock references.

Не возвращать arbitrary Blender dumps.


==================================================
11. FLOAT COMPARISON
==================================================

Не вводить глобальный произвольный fuzzy tolerance.

Сначала использовать фактическое representation Blender.

Если конкретному property нужна normalization,
она должна быть:
- обоснована;
- локальна;
- протестирована.

Не скрывать реальные пользовательские изменения
из-за слишком большого tolerance.


==================================================
12. RESULT STATE
==================================================

После Compare Parameters
Astro Modeler хранит небольшой runtime inspection result.

Например:

Object: Body
Modifier: Bevel
Type: BEVEL

Changed properties:
- width
- segments
- limit_method

Этот result нужен:
- для отображения в Blender UI;
- для последующего optional AI explanation.

Не хранить его в Scene/.blend,
если это не требуется.


==================================================
13. OPTIONAL AI EXPLANATION
==================================================

После того как локальный diff уже существует,
пользователь МОЖЕТ при желании использовать AI.

Это ВТОРАЯ функция.

Например отдельный блок:

AI EXPLANATION

Context:
[...........................]

[ Explain Changes ]


AI не участвует в вычислении diff.

Он получает уже готовые факты.


==================================================
14. DEFAULT AI INSTRUCTION
==================================================

В проекте должна быть стандартная инструкция
для объяснения modifier diff.

Например:

"Объясни простым русским языком,
что делают изменённые параметры,
как текущее значение отличается от Blender default
и зачем моделлер мог это изменить.
Не выдавай предполагаемое намерение автора за факт."


Пользователь НЕ обязан каждый раз писать этот prompt вручную.


==================================================
15. OPTIONAL CONTEXT
==================================================

Context является НЕОБЯЗАТЕЛЬНЫМ.

Если поле пустое:
использовать standard AI explanation instruction.

Если пользователь написал:

"Объясни как ребёнку."

или:

"Меня интересует 3D-печать."

или:

"Объясни влияние на производительность."

этот текст ДОПОЛНЯЕТ стандартную инструкцию.


Наличие пустого context
НЕ отключает локальное сравнение.


==================================================
16. ВАЖНО: ДВЕ ОТДЕЛЬНЫЕ ОПЕРАЦИИ
==================================================

Не делать одну кнопку,
которая непонятно одновременно считает и вызывает AI.

UX должен ясно разделять:

[ Compare Parameters ]

и

[ Explain Changes ]


Сначала пользователь получает FACTS.

Потом сам решает,
нужна ему INTERPRETATION или нет.


==================================================
17. AI EXPLANATION — FACTS VS INTERPRETATION
==================================================

Пример deterministic fact:

segments:
Default: 2
Current: 6


AI может сказать:

"Segments определяет количество сегментов скругления.
Значение увеличено с 2 до 6,
поэтому фаска обычно выглядит плавнее."


А фраза:

"Автор сделал это специально ради красивого блика"

НЕ является доказанным фактом.

Использовать:

"Вероятно..."
"Обычно это делают..."
"Это могло быть сделано для..."


==================================================
18. EDUCATIONAL VALUE
==================================================

Это важная часть продукта.

Например начинающий пользователь
открывает старую или чужую модель.

Он видит Bevel,
но не понимает настройки.

Compare Parameters говорит:

"Изменены Width, Segments, Limit Method."

AI Explanation затем может сказать:

"Width — ширина фаски.
Здесь её сделали значительно меньше стандартной,
поэтому края модели остаются более острыми."

Так инструмент одновременно:
- анализирует;
- обучает.


==================================================
19. ГДЕ ПОКАЗЫВАТЬ AI EXPLANATION
==================================================

Полный длинный AI explanation
предпочтительно показывать в conversation Codex Agent.

Blender UI не нужно превращать

Blender panel показывает:
- object;
- modifier;
- compact diff;
- optional context;
- status.


==================================================
20. КАК ЗАПУСКАЕТСЯ AI EXPLANATION В V1
==================================================

Текущая архитектура Blender plugin
не умеет сама инициировать сообщение
в существующий Codex conversation.

Поэтому не строить reverse chat transport
в TASK 016.

V1 может работать так:

1. пользователь уже получил diff в Blender;

2. optional context сохранён;

3. пользователь просит Codex Agent:
   "Объясни изменения выбранного модификатора."

4. Codex Agent вызывает controlled inspection/result tool;

5. получает compact diff + optional context;

6. объясняет.


Future:
Blender button → automatic Agent request
можно реализовать отдельно.


==================================================
21. PUBLIC MCP TOOL
==================================================

Нужен controlled read-only inspection tool,
чтобы Codex Agent мог получить последний/current diff.

Рабочее имя:

inspect_selected_modifier_changes()

или аналогичное ясное имя.


Он НЕ должен создавать новый semantic diff моделью.

Он получает deterministic Blender result.


Если при tool call diff ещё не рассчитан,
можно:
A. выполнить тот же deterministic comparison;
или
B. честно потребовать Compare Parameters сначала.

Выбрать наиболее простой и однозначный contract.

22. THIRD-PARTY / SPECIAL MODIFIERS

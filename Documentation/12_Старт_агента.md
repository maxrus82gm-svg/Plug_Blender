# START — работа с TASK

Канонический источник task-loop: постановка → execution → AGENT REPORT → AGENT REVIEW → INDEPENDENT REVIEW. Повседневные решения и границы автономности определены в правилах агента (`Documentation/10_Правила_агента.md`).

## Маршрут чтения

В начале новой рабочей сессии и перед выбором следующей задачи обязательно прочитай короткий актуальный handoff `Documentation/13_Приоритетная_задача.md`. Он восстанавливает только принятое следующее направление, если conversational context недоступен, устарел или потерян.

Затем начни с БЛОКА 1 текущей TASK (`Documentation/11_Задача_агенту.md`). Большой и Малый блоки задают минимальное обязательное чтение: конкретные документы и, где достаточно, разделы. Рабочий контекст составляют актуальное состояние (`Documentation/01_Текущее_состояние.md`), релевантные правила, технический / архитектурный материал и нужный код. Не перечитывай автоматически весь START, архитектуру или локальную Blender-базу; открывай требуемые разделы. Накопленный БЛОК 2, старые AGENT REPORT и история задач не являются обязательным контекстом новой TASK: обращайся к конкретному прошлому факту только при необходимости.

**READ WHAT IS REQUIRED, NOT EVERYTHING AVAILABLE.** Правила размещения знаний — `Documentation/20_SplitDoc/DOCUMENTATION_RULES.md`.

| Тема | Канонический источник |
| --- | --- |
| Documentation, Markdown, перенос правил | `Documentation/20_SplitDoc/DOCUMENTATION_RULES.md` и `Documentation/20_SplitDoc/ENCODING_RULES.md` |

## Постановка и запуск

Перед подготовкой / запуском новой самостоятельной TASK ChatGPT проверяет, закрыта ли предыдущая: получен ли AGENT REPORT и завершено ли INDEPENDENT REVIEW. Если нет, переход останавливается с напоминанием закрыть предыдущий этап. Исключение — пользователь явно отменяет / откладывает предыдущую TASK или прямо разрешает нарушить последовательность. Обычные уточнения и REVIEW CORRECTION той же TASK этой проверки перехода не требуют.

### Research-First: подготовка технического контекста

Для обычной плановой технической TASK ChatGPT до её постановки определяет необходимые технические сведения и при необходимости исследует официальную документацию Blender, SDK и библиотек. В задание входят минимально достаточные подтверждённые факты, источники, существенные версии и конкретные разделы для чтения; предположения обозначаются отдельно. Astra начинает с подготовленного контекста и фактического кода, а не с широкого повторного исследования.

Если требуется новое устойчивое знание, ChatGPT передаёт выжимку и источники в постановке; Astra в разрешённой документационной части сначала создаёт или обновляет короткую technical note, затем использует её при реализации той же TASK. Отдельная административная задача для каждой маленькой заметки не нужна. Большое или архитектурно значимое исследование может стать отдельной research/documentation TASK. Критерии заметок — в DOCUMENTATION_RULES; точечный fallback research и аналитическая самостоятельность Astra — в правилах агента (`Documentation/10_Правила_агента.md`).

Одна `TASK XXX` по возможности является маленьким независимым законченным шагом. Большую работу делят на последовательные задачи, если это сохраняет целостность результата.

### Рекомендация Codex Agent

Перед Большим блоком каждой новой TASK ChatGPT обязательно даёт пользователю отдельную короткую рекомендацию модели и уровня рассуждения Codex Agent. Модель выбирается по доступности и сложности TASK; она не является архитектурной зависимостью проекта. Шкала уровня: **LOW / НИЗКИЙ**, **MEDIUM / СРЕДНИЙ**, **HIGH / ВЫСОКИЙ**, **VERY HIGH / ОЧЕНЬ ВЫСОКИЙ**. Формат, например:

```text
РЕКОМЕНДАЦИЯ ПО CODEX AGENT:
MODEL: GPT-5.6 Sol
LEVEL: MEDIUM / СРЕДНИЙ
```

При необходимости добавляется одна короткая причина. Рекомендация помогает пользователю выбрать режим перед запуском; она остаётся вне Большого и Малого блоков, не является заданием или инструкцией модели и не переключает её режим автоматически.

Учитывай архитектурную сложность, неоднозначность, потребность в исследовании, риск ошибки, размер и сложность изменения, согласование документов / подсистем и стоимость контекста. Для механических, определённых и локальных задач предпочитай LOW или MEDIUM. HIGH / VERY HIGH рекомендуй только когда дополнительное рассуждение улучшает результат; высокий уровень не является автоматическим выбором. LOW не объявляется автоматически достаточным для всех будущих TASK. Контекст Codex Agent — ограниченный ресурс.

### Универсальный протокол «Большой блок + Малый блок»

**БОЛЬШОЙ БЛОК** — полная постановка TASK. Он хранится в БЛОКЕ 1 `Documentation/11_Задача_агенту.md` и отвечает на вопрос **«ЧТО именно делать»**: номер и название, цель, контекст, необходимое чтение, действия, scope, разрешённые и запрещённые изменения, проверки и формат отчёта. Постоянные правила передаются ссылками.

**МАЛЫЙ БЛОК** — короткое стартовое сообщение агенту. Он отвечает на вопрос **«ЧТО сейчас открыть и ЗАПУСТИТЬ»** и не дублирует полную постановку. В нём указываются:

- номер и название запускаемой TASK;
- путь к БЛОКУ 1;
- что обязательно прочитать перед этой конкретной задачей;
- команда начать выполнение;
- при необходимости только короткие актуальные уточнения, которых ещё нет в Большом блоке.

Если конкретной TASK нужны дополнительные документы, Малый блок — удобное место явно перечислить их. Он не является новой TASK и не заменяет БЛОК 1.

Этот протокол является универсальным механизмом документационной системы, а не особенностью Plug_Blender. При переносе шаблона в другой проект сохраняются оба блока, их назначение и порядок запуска; меняются только проектные пути и содержание конкретной TASK.

Пример Малого блока:

```text
Запусти TASK XXX — Название.
Полная постановка: БЛОК 1 Documentation/11_Задача_агенту.md.
Перед исполнением прочитай этот БЛОК 1 и указанные здесь документы / разделы:
актуальное состояние, нужные разделы START / правил и подготовленный технический контекст TASK.
Начни выполнение в указанном scope. После AGENT REPORT и AGENT REVIEW остановись и ожидай INDEPENDENT REVIEW.
```

При прямой передаче полного задания пользователем в чат или вложении оно уже является основанием работы: отсутствие его копии в БЛОКЕ 1 не требует повторного разрешения. Если TASK разрешает ведение task-loop, агент фиксирует актуальное задание в БЛОКЕ 1 перед исполнением.

Дополнения до первого AGENT REPORT относятся к текущей TASK. Мелкое уточнение не требует переписывать весь БЛОК 1. Существенное изменение цели, архитектуры или scope согласуется по правилам агента (`Documentation/10_Правила_агента.md`). Передаваемые задания, уточнения и corrections оформляются цельными блоками для копирования, с пояснениями вне блока.

### Verification plan и остановка

До существенных проверок Codex Agent кратко фиксирует минимальный `VERIFICATION PLAN` по рискам изменённой части: targeted/static/unit, при необходимости один Blender runtime, real model acceptance только для model/MCP поведения и manual visual acceptance только для недоказуемого автоматически UX. План не является отдельным документом.

Проверки прекращаются, когда acceptance criteria доказаны, релевантная regression зелёная, новых ошибок или неопределённостей нет, а следующий check дублировал бы имеющееся доказательство. Не расширяй testing только потому, что доступны дополнительные harness или сценарии. После локальной test-only ошибки повторяй затронутый уровень и минимальную regression, а не всю цепочку без нового риска. Подробная классификация и уровни — в `Documentation/10_Правила_агента.md`.

## Исполнение и отчёт

Агент выполняет TASK и релевантные проверки. При разрешённом обновлении документации записывает AGENT REPORT в БЛОК 2 и краткий итог в `Documentation/20_SplitDoc/История_задач.md`. Если документационные изменения вне scope, отчёт выдаётся в чате без самовольной правки файлов.

Базовый AGENT REPORT содержит TASK, STATUS, `AGENT MODEL`, `AGENT LEVEL`, `ESCALATION`, READ, списки созданных / перенесённых / изменённых / удалённых файлов, выполненную работу, CHECKS, UNEXPECTED CHANGES, PROBLEMS, QUESTIONS, RECOMMENDED NEXT TASK, GIT и CONCLUSION. При смене уровня также указываются переход и причина. Конкретная TASK может уточнять структуру. Объём отчёта соответствует работе; непроведённые проверки обозначаются явно.

После AGENT REPORT агент записывает AGENT REVIEW — собственную оценку выполненного, проверок, непроверенного, проблем и ограничений, с собственным выводом. Самооценка может быть ошибочной; даже положительный вывод не является окончательным принятием TASK. Статус после неё — AWAITING INDEPENDENT REVIEW. Объём обоих разделов соразмерен задаче.

После завершения исполнения и записи отчёта и самооценки БЛОК 1 очищается до трёх строк:

```text
Активной задачи на исполнение нет.
Результат предыдущей задачи ожидает INDEPENDENT REVIEW.
Следующая задача не запущена.
```

Заголовки БЛОКОВ 1–3 сохраняются по одному. БЛОК 2 содержит последний AGENT REPORT и AGENT REVIEW, БЛОК 3 — статус AWAITING INDEPENDENT REVIEW. Исторические отчёты сохраняются без переписывания под новую терминологию. Это закрывает исполнение, но не означает PASS. При BLOCKED или незавершённой работе задание в БЛОКЕ 1 сохраняется с описанием препятствия.

## Review и corrections

Источник проверяемого результата и различие local / remote review оформляются по `Documentation/20_SplitDoc/GIT_REVIEW_RULES.md`.

**AGENT REVIEW** выполняет исполнитель Codex / Astra как собственную оценку работы. **INDEPENDENT REVIEW** выполняет внешний проверяющий ChatGPT / пользователь; только этот уровень определяет окончательный статус TASK. Он сопоставляет фактический результат с заданием и самооценкой, а не принимает её на доверии. Агент не объявляет свою TASK принятой.

После получения AGENT REPORT + AGENT REVIEW ближайший обязательный этап — немедленное INDEPENDENT REVIEW:

```text
AGENT REPORT + AGENT REVIEW → INDEPENDENT REVIEW → дальнейшее обсуждение / следующая TASK
```

Это порядок взаимодействия ChatGPT / пользователя с исполнителем, а не механизм технического управления ChatGPT из репозитория. Обсуждать идеи и будущие задачи можно, но review предыдущей TASK не должно теряться или молча откладываться. Если фактический источник недоступен, проверяющий явно фиксирует `INDEPENDENT REVIEW — TASK XXX: AWAITING SOURCE` и кратко указывает, какой источник нужен. Review остаётся открытым до проверки доступного результата; отсутствие источника не означает PASS.

Если результат доступен для реальной проверки и проверка не выявила ошибок или расхождений, достаточно:

```text
INDEPENDENT REVIEW — TASK XXX
REVIEW CONFIRMED.
VERDICT: PASS.
```

Допускается одна короткая существенная заметка. Независимому review не нужно дублировать AGENT REPORT, файлы и тесты ради объёма. Если самооценка ошибочна, неполна или результат не соответствует TASK, проверяющий кратко указывает расхождение и соответствующий verdict.

Недоработка внутри исходного scope оформляется как `REVIEW CORRECTION — TASK XXX`: тот же номер и название, путь `Documentation/11_Задача_агенту.md`, недостаток, требуемое исправление и необходимые проверки. БЛОК 1 заново не создаётся; correction и контекст исходной задачи задают разрешённое исправление. Агент обновляет AGENT REPORT, AGENT REVIEW и историю, оставляет БЛОК 1 с заглушкой и снова ожидает INDEPENDENT REVIEW.

До PASS такие corrections остаются частью той же TASK и не получают нового номера. Существенно новая работа или выход за исходный scope требуют отдельного решения и новой TASK.

Явное `TASK XXX — PASS` или однозначное принятие пользователем / ChatGPT в чате достаточно для завершения review. Обязательное дополнительное сообщение REVIEW RESULT не требуется. Полученный внешний verdict можно передать агенту коротким сообщением и синхронизировать в документации без новой большой постановки либо записать в начале следующей TASK. Отдельная административная TASK не нужна. Агент фиксирует переданный verdict как факт, не переосмысливая его самостоятельно.

## История и следующая задача

История задач — краткая хронология проекта, а не полная база знаний. Для TASK достаточно номера / названия, цели, фактического результата, существенных corrections и итога INDEPENDENT REVIEW; при необходимости добавляется маршрут к тематическому документу. Полный AGENT REPORT, отдельный REVIEW_HISTORY и длинные технические объяснения туда не переносятся. Долговечные знания размещаются по `Documentation/20_SplitDoc/DOCUMENTATION_RULES.md`.

### Жизненный цикл очереди, приоритета и истории

Эти источники не дублируют друг друга:

- `Documentation/05_Очередь_задач.md` — живая очередь того, что ещё предстоит выполнить. Завершённая задача удаляется из активной очереди, если присутствовала там как ожидающая работу.
- `Documentation/13_Приоритетная_задача.md` — ровно текущее решение «что собираемся делать следующим». Это не backlog и не история. После закрытия приоритетной задачи файл заменяется следующей выбранной задачей; если она ещё не выбрана, файл прямо сообщает, что следующий приоритет пока не определён.
- `Documentation/20_SplitDoc/История_задач.md` — каноническая хронология реально завершённых задач в существующем формате проекта. Новый параллельный журнал завершённых задач не создаётся.

Окончанием реализации задача не закрывается. Для обычного review workflow закрытие наступает только после полной цепочки:

```text
AGENT REPORT → AGENT REVIEW → INDEPENDENT REVIEW → VERDICT: PASS
```

Только после финального PASS одновременно выполняется движение: задача уходит из активной очереди, факт завершения фиксируется в `История_задач.md`, а priority file получает следующую выбранную задачу или явное состояние «не определена». До PASS задача не переносится в completed/history и не освобождает текущий приоритет. В частности, TASK 016 остаётся незакрытой до пользовательского Level D, AGENT REPORT, AGENT REVIEW и итогового independent review.

После PASS следующая TASK получает следующий номер и запускается новой постановкой. При её запуске агент синхронизирует в истории подтверждённый итог предыдущей задачи, если он ещё не записан; отдельная административная TASK для этого не нужна. Наличие следующего пункта в очереди не разрешает запускать его автоматически.

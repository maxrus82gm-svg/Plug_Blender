# DOCUMENTATION RULES

Канонические правила ведения документации Plug_Blender. Для чтения и записи текста применяются `Documentation/20_SplitDoc/ENCODING_RULES.md`.

## Пути и источники

Активная база — `Documentation/`. Постоянные пути в тексте, TASK и сохранённых отчётах задаются относительно корня репозитория. Markdown-ссылки разрешаются относительно содержащего их файла. Машинно-зависимый абсолютный путь допустим в разовой диагностике, но не становится постоянным проектным путём.

Каждое постоянное правило имеет один канонический источник. В других документах остаётся ссылка или краткий маршрут. Перед добавлением документа проверь, решает ли его задачу существующий файл; пустые документы «на будущее» не создаются.

## Обновление и миграция

Адаптируй смысл перенесённого текста: чужие предметные факты, архитектура и история не становятся фактами проекта. Подтверждённую концепцию отделяй от реализации, исследуемые варианты — от решений, идеи — от обязательств.

Перенос документации включает проверку входящих ссылок и уникального содержания. Старый каталог удаляется только после проверки результата и при разрешённом scope. Служебные настройки редактора оцениваются по фактическому содержимому: полезные настройки можно сохранить при миграции, но они не являются проектными правилами. Изменение или перенос осмысленной конфигурации явно отмечается в отчёте; обычное пользовательское `workspace*.json` Obsidian оценивается по специальному правилу в `Documentation/20_SplitDoc/GIT_REVIEW_RULES.md` и отдельного замечания не требует.

Устаревшие предметные правила исключаются из активной системы. Тематические правила новых технологий появляются лишь при подтверждённом содержании и практической необходимости; наличие старого аналога не является причиной создавать новый файл.

## Тематические документы и экономия контекста

Документация должна позволять читать минимально достаточный набор источников. START маршрутизирует к конкретной TASK, текущему состоянию, релевантным каноническим правилам и проектным документам; история нужна только для исторического контекста. Не требуй перечитывания всей `История_задач.md` или всех прежних AGENT REPORT для обычной новой задачи. Формат краткой хронологии истории задач определён в START.

Подробное описание хранится в одном каноническом месте. В истории задач, текущем состоянии, архитектуре, AGENT REPORT и Project_Doc не дублируй его одновременно: остальные документы дают краткий итог и маршрут. Отчёт фиксирует выполненное и проверки; тематический документ описывает долговечное знание, доступное независимо от конкретной TASK.

Отдельный документ допустим для самостоятельной долговечной сущности, подсистемы, data contract, механизма анализа, workflow или стандарта, к которому будущие задачи будут обращаться независимо от истории. Сначала проверь существующий канонический документ. Новый файл нужен только если сущности требуется собственное описание или существующий документ смешивает разные темы; документ на каждую TASK не создаётся.

- `20_SplitDoc` — переносимые правила рабочего процесса, документации и Git/review.
- `21_Project_Docs` — сущности Plug_Blender / Astro Modeler, подсистемы, технические контракты и пользовательские инструкции.

При выделении нового тематического документа обнови соответствующий индекс. Если нового документа нет, индексы только ради TASK не меняй; правила актуализации навигации при фактическом переносе сохраняются.

## Локальная техническая база знаний

Сохраняй короткие собственные технические выжимки, а не копию Blender Manual, длинные цитаты или единую «Blender Bible». Знание должно уже понадобиться реальной TASK, быть подтверждённым, вероятно востребованным снова и дорогим для повторного исследования. Например, сведения о Cursor, origin/pivot, world/local space, matrix_world, Empty, dimensions/scale, Boolean, Mesh selection, modifiers или bpy context/mode добавляются по реальной потребности, а не заранее списком пустых документов.

Сначала используй существующий канонический документ; отдельная небольшая тема оправдана, когда её нужно читать независимо. Проектные technical notes относятся к `21_Project_Docs`, переносимые правила процесса — к `20_SplitDoc`. Порядок подготовки заметки до реализации в рамках той же TASK задан в START; документационная запись требует разрешённого scope.

Приоритет технических источников: официальная Blender Documentation / Python API или документация используемого SDK; фактическое поведение установленной версии; исходный код / проверенный эксперимент, если описания недостаточно. Укажи первоисточник, значимую версию API, подтверждённое поведение и ограничения. Предположения не записываются как факты.

Agent Feedback / MODELING NOTE помогает отличить нехватку tool от нехватки технических знаний, пользовательского контекста или ошибки реализации. Пользователь и ChatGPT определяют причину; если не хватает знания, ChatGPT исследует тему перед следующей TASK, а подтверждённая полезная выжимка при необходимости пополняет базу. База растёт из практических затруднений, без автоматического расширения scope.

`_research/` — локальная игнорируемая Git папка для внешних reference-проектов. Она не входит в Plug_Blender и не отправляется на GitHub; содержимое используется только для исследования и сравнения решений. Чужой код не становится частью Astro Modeler автоматически. Прямое заимствование требует отдельного осознанного решения с проверкой лицензии и происхождения. Наличие решения в reference-проекте не обязывает Astro Modeler повторять его архитектуру.

## Markdown

- Один понятный заголовок первого уровня на документ; разделы и короткие обычные списки.
- Настоящие переносы строк, корректно закрытые code fences, пустые строки перед списками и после заголовков.
- Внутренние ссылки ведут к существующему файлу и, если указан, к существующему разделу.
- Навигационные индексы обновляются вместе с переносом и изменением назначения документов.

## Проверка документационной правки

Проверь изменённый материал: структуру и читаемость Markdown, внутренние ссылки, encoding, соответствие проектному контексту и scope. При миграции дополнительно проверь отсутствие активного чужого контекста, устаревших канонических путей и противоречащих дублей. Diff и новые untracked-файлы проверяются по `Documentation/20_SplitDoc/GIT_REVIEW_RULES.md`.

Общая соразмерность проверок определена в правилах агента (`Documentation/10_Правила_агента.md`), формат отчёта — в START (`Documentation/12_Старт_агента.md`).
